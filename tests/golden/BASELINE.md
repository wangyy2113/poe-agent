## 首次基线暴露的四个缺陷

评测的价值就在这里：四条失败用例各自指向一个具体缺陷，且都不是「调参数」能解决的。

### 1. 别名精确命中会掩盖「维度无数据」（2 条漏出）

- `gap_price_headhunter`「猎首现在值多少混沌石」→ alias 命中 `unique_item:Headhunter`
  → `sufficient=true`，理由「实体精确命中」。但价格维度 `economy_price = not_collected`，
  库里一个字都没有。
- `gap_passive_path_cost`「从起点点到神威之盾要花几个天赋点」→ alias 命中天赋节点
  → 判充分。但 `passive_tree` 的 `partial_note` 明确写着「天赋点消耗与连接关系未入库」。

根因：充分依据判定只问「查询词/实体是否出现在库里」，**不问「被问的那个维度有没有数据」**。
而 `kb/coverage.py` 已经有 domain × status 的自描述层，`attribute_gap()` 也已经能归因，
但检索侧的判定没有咨询它。

修法方向：在 `retrieval.hybrid.retrieve()` 判定为充分之后（或 `orchestrator/loop.py`
进入生成之前）加一道维度覆盖检查——问题命中的领域若 `status` 为 `not_collected` /
`harvested`，或 `partial_note` 明确排除了被问的维度，则即使实体精确命中也走缺据声明，
并且能说清是「未采集」而不是「查不到」。风险是引入新的错误拒答（问「猎首有哪些词缀」
不能被误拦），所以必须成对监控——现在有尺子了。

### 2. 通用词凑够覆盖率造成漏出（1 条）

`gap_skill_gem_numbers`「冰霜脉冲在 20 级时的基础伤害是多少」→ 覆盖率 75% 过线，
top 命中的是唯一装备「初雪」。技能石一条未入库，但「冰霜」「伤害」这些词在库里到处都有，
`absent_from_corpus` 因此不触发。同 1 的修法可一并解决（`skill_gem = harvested`）。

### 3. 口语同义词误触 `absent_from_corpus`（1 条错误拒答）

`num_belt_strength_t1`「腰带上力量词缀的最高档位是多少」→ 覆盖率 80% 达标、正确的卡
`mod_ladder:Belts:Strength` 也召回了，却因为「**档位**」这个词全库为零而判定不足。

「档位」是用户口语，库里用「T 级 / 阶级 / 梯度」——而它**已经登记在**
`retrieval/hybrid.py` 的 `_MOD_INTENT_TERMS` 里。`absent_from_corpus` 的设计意图是抓
「玄虚之靴」「流放之路2」这类**专名不存在**的情况，对意图词误伤。

修法方向：`absent_from_corpus` 判定前剔除已登记为意图词的词——意图词表达「想问哪类信息」，
不是问题主体。

### 4. `min_coverage` 在本集上几乎是惰性参数

| min_coverage | 错误拒答 | 漏出 | Recall@20 |
| --- | --- | --- | --- |
| 0.30 | 1/27 | 3/13 | 100% |
| 0.40 | 1/27 | 3/13 | 100% |
| **0.50（当前）** | **1/27** | **3/13** | **100%** |
| 0.60 | 1/27 | 3/13 | 100% |
| 0.70 | 2/27 | 3/13 | 100% |
| 0.80 | 2/27 | 2/13 | 100% |

0.30–0.60 完全同结果：两条漏出走 `exact_hit` 分支，根本不经这个阈值；第三条要拉到 0.80
才拦住，代价是拦掉一条正常的描述性查询（`desc_steal_mods_belt`）。

**结论：保持 0.50，不动。** 漏出要靠上面三条逻辑修复，调这个参数只会用错误拒答换漏出。
这条结论本身就是评测存在的理由——在此之前「调高一点是不是更安全」这个问题没有答案。

**好消息是流式与批量判定 100% 一致**——这条不变量先前只有 10 组手写文本 × 4 种切片在守，
现在有 32 条真实模型输出 × 3 种切片作证。17 条的输出差异全是空白字符（1 字符切片时
`# 标题\n\n` 与 `# 标题\n` 的换行归属不同），判定与用户可见内容一致，因此单列不计入失败。

### 主要发现：48% 的拦截是 Markdown 表格行

192 句拦截里 **92 句（48%）** 是表格行，两种形态：

```
| T 级 | 词缀文本 | 物品等级 | 生成权重 |          ← 表头，被判「事实句未绑定引用」
| T1/1 | …转化为生命偷取 | 60 | 3000（16.575%） |   ← 数据行，同样未绑定
| 3 | +(50-60) 最大生命[[E1]] |                    ← 序号列的「3」被要求溯源
```

根因：`orchestrator/binding.is_structural` 不认识 Markdown 表格。分句按行切开后，
表头行与分隔行不承载断言却被判事实句；数据行里的序号列被当成待溯源数值
（「数值 3 未出现在绑定证据 E1 中」，那个 3 是行号）。

**这会同时污染两个方向**：错误拒答（合法表格被撕碎）与指标可信度（引用有效率被压低近一半，
掩盖了真实的漏出情况）。修法有两条路，取舍不同：

1. **闸门认表格**：`is_structural` 识别表头/分隔行，数据行按单元格校验而不是整行。
   保留模型用表格的能力，但闸门要理解一种新的结构。
2. **答案契约禁表格**：提示词明确要求用列表而不是表格。闸门逻辑不变，
   代价是答案表达受限（词缀档位这类数据用表格确实更清晰）。

两条都不该拍脑袋定——它改的是用户看到的答案形态。

### 工具路由：3/6

| 用例 | 期望 | 实际 |
| --- | --- | --- |
| `route_mod_tiers` | `mod_tiers` | 只调了 `kb_search`（且判为依据不足） |
| `route_entity_lookup` | `entity_lookup` | 只调了 `kb_search` |
| `route_kb_coverage` | `kb_coverage` | 只调了 `kb_search`（且判为依据不足） |
| `route_stat_sources` / `route_check_mod_combination` / `route_bench_recipe` | — | 命中 |

`ALLOWED_TOOLS` 的顺序即推荐优先级、提示词也逐条写了选工具的规则，但模型在三类问题上
仍退回全文检索。`route_mod_tiers`（「腰带上的力量词缀一共有几档」）本该由 `mod_tiers`
精确回答，走 `kb_search` 则退化成命中一张卡再读表格——正是提示词里明确要避免的情形。
这是提示词与实际行为的差距，值得单独一轮处理（可能要把工具选择从提示词建议改为代码路由，
就像 `_precision_tool_route` 已经为 `affix_pool_odds` 与 `bench_recipe_catalog` 做的那样）。

### 表格修复后（同日，同一批录制回放）

选的是「闸门认表格」：`split_sentences` 把连续表格行合成**一个断言单位**，
绑定标记出现在表内任何位置都对整张表生效；数值仍逐个回填校验，只有确认为
**序号列**（某列在全部数据行上都是纯整数且构成 1..n 连续序列）的数字不参与。
流式侧配套改动：表格没收齐**不下发**，否则流式按行校验、批量按整块校验就分叉了。

| 指标 | 修表格前 | 修表格后 |
| --- | --- | --- |
| 引用有效率 | 45%（154/346） | **56%（150/270）** |
| 拦截 | 192 句 | **120 句** |
| 其中表格相关 | 92 句（48%） | **15 句（12%，且都是真问题）** |
| 流式与批量判定一致 | 32/32 | **32/32** |
| 单测 | 299 | **309**（新增 10 项表格用例） |

剩下的 15 句表格拦截是真问题：模型整张表都没绑定，或某个数值确实不在证据里。

修的过程中把最关键的不变量弄坏过一次，两个坑都值得记下：

- **表格未收齐就下发**：`_take_sentence` 原先只判「只剩表格一段」，可下一行只写到 `|`
  时 split 会切出两段，于是上一行被提前放行——流式与批量的一致率从 32/32 掉到 18/32。
  判据要补上「缓冲区最后一行还在表内」。
- **`_is_table_line` 认不出自己合并出来的块**：`^\|.*\|$` 里的 `.` 不匹配换行，
  多行块必然返回 False；行末的 `|[[E1]]` 也会让 `\|\s*$` 匹配不上，
  于是**带引用的表格行反而认不出是表格**，正好是最该放行的那一类。
  两处都要先剥绑定标记、只看首行。

### 4 条错误拒答里 3 条是同一个根因：过渡句与缺据声明的白名单太窄

| 被拦的句子 | 为什么该放行 | 卡在哪 |
| --- | --- | --- |
| 「以下按渠道逐一列出，并在最后说明覆盖限制。」 | 纯元话语，无事实无数值 | `_NARRATIVE_RE` 的 12 字上限 |
| 「该核心节点具有以下效果：」 | 纯引导句 | `_NARRATIVE_RE` 锚定句首，「以下」在句中匹配不上 |
| 「根据结构化词缀库的直接查询…均返回无匹配结果」 | **已限定范围的缺据声明**，正是无据不答希望模型说的话 | `_DISCLOSURE_RE` 没覆盖「均返回无匹配结果」构式 |
| 「证据 [E2]–[E8] 全部为…与技能石数值无关。」 | 对证据本身的说明，属缺据声明 | `_DISCLOSURE_RE` 没覆盖「与…无关」 |

**放宽白名单必然抬高漏出风险**，所以改完必须两个池一起重测——现在两个池都有基线数字，
可以做到这一点。这是下一轮最该做的事。

另外两条值得记的观察（不算错误拒答，但都是模式）：

- **列表项的绑定与表格同类**：`name_abberaths_horn_slug#4`（「- 攻击和法术附加 (1-2)-(3-4)
  基础火焰伤害」）的数值确实在 E1 里，模型把标记标在列表标题上、逐条列项不带标记，
  于是每一项都被拦。表格已经按「整块一个断言单位」解决，列表是不是同类值得单独量一次。

  引用列表由系统生成」。是格式违规不是无据，闸门放行是对的，但会让引用出现两套形态。

## 2026-08-17 · 第三轮：放宽白名单，压错误拒答

上一轮审计判出 4 条错误拒答（33%），3 条是白名单太窄。这一轮按「每放行一类就配一条
换个说法必须拦的反例」的方式放宽，改了四处，全部在 `orchestrator/binding.py`：

| 改动 | 覆盖的错误拒答 |
| --- | --- |
| `_DISCLOSURE_RE` 补「查询无结果」「与…无关」构式 | 「…均返回无匹配结果」「…与技能石数值无关」 |
| `_DISCLOSURE_RE` 允许否定词与动词间夹量词 | 「…没有**一条**涉及偷取」 |
| 新增 `_COLON_LEAD_IN_RE`（引导词 + 冒号收尾、整句无逗号、无数值） | 「该核心节点具有以下效果：」「显式词缀如下：」 |
| `is_structural` 剥标题前导序号、识别纯 URL 行 | 「### 1. 装备词缀」「https://poedb.tw/cn/Skill_Gems」 |

`_COLON_LEAD_IN_RE` 有两个刻意的设计，别改掉：

- **放在领域词判定之前**。`显式词缀如下：` 里的「词缀」是 `factual_terms` 成员，
  按原顺序会先被判成事实句。这类引导句在本领域答案里极常见，拦它等于把答案结构撕碎。
- **整句不含逗号**。逗号意味着有子句，也就是可能夹带断言——
  `猎首会偷取词缀，说明如下：` 因此不放行。单纯放宽 `_NARRATIVE_RE` 的前缀做不到这一点。

**没有**放宽 `_NARRATIVE_RE` 的 12 字尾部上限：尾部允许长内容会直接重开
「既无数值也无领域词的编造机制句」那个洞（`classify` 的 docstring 里记着这笔账）。
代价是「以下按渠道逐一列出，并在最后说明覆盖限制。」这类长引导句仍被拦。

### 一个读数上的坑：blocked 池是「当前仍被拦的句子」

错误拒答率的分母是**当前**被拦的句子。每修好一类误拦，那些句子就退出池子，
轮转抽样会补进新的——所以这个比率是**条件于当前闸门**的，不能跨轮次直接比绝对值。
本轮实际走了 33% → 11% → 25% → 10% → 9% → 17% 这么一串，每次波动都是池子换了成分，
不是闸门反复变好变坏。跨轮次要看的是**拦截总数**（192 → 106）与**已修类别数**。

判到最后一条时主动停手：`「直接在腰带底材上查询偷取相关关键词也无任何结果。」`
（缺据声明的名词收尾形，`无 + 量词 + 结果/记录/条目`）已确认是误拦但**本轮不修**——
每修一条就有新句子进池，再迭代会开始过拟合这 24 条样本。它和长引导句一起留给下一轮，
下一轮该先把抽样量加大到 40–50 条再动手。

## 2026-08-18 · 工具路由落到代码

上一轮基线里工具路由只命中 3/6：`mod_tiers` / `entity_lookup` / `kb_coverage` 三类问题
模型仍退回 `kb_search`，而提示词已经逐条写了选工具规则。这一轮把路由从提示词改成代码判定。

### 关键实测：这个网关**完全忽略 `tool_choice`**

第一版用协议层的 `tool_choice` 强制调用，结果模型照旧不调。单独探测确认：

| `tool_choice` | 结果 |
| --- | --- |
| 不传 / `auto` / `required` / 指定函数名 | **四种写法 `tool_calls` 全为 0** |

探针是「`tools=[get_weather]` + 用户说『随便聊两句，不要查任何东西』」，
连 `required` 都不产生调用。所以在这个网关上「强制调用」只有两条路：
**代码自己调**，或**把别的选项从 schema 里拿掉**。两条都用上了：

- `entity_lookup` / `kb_coverage`：参数能在代码里推导（前者路由时已确认名字命中别名表，
  后者无参数）→ **由代码直接调用**，与强制检索 `kb_search` 同一个模式，模型没有裁量权。
- `mod_tiers` / `stat_sources`：参数需要拆解问题 → 第一轮**只 offer 这一个工具**。
  强制检索已由代码跑过，模型这一轮没有理由退回 `kb_search`。

还有一处架构缝要补：偏好路由必须和精确路由一样**豁免「检索不足」**。
「你的库覆盖哪些领域」「某属性从哪来」的证据本来就不在 chunk 里，BM25 命不中是正常的；
不豁免的话整轮在进生成前就被判缺据，工具根本没机会调。兜底是「跑完一条证据都没拿到仍走
缺据声明」，避免答案带着零证据进闸门被撕碎。

### 覆盖声明改为代码生成

`kb_coverage` 接通后立刻暴露一个质量回退：模型转述覆盖清单，产出 33 句带数字却无引用的
句子，**全部被闸门拦下**，该子集引用有效率从 59% 掉到 13%——用户看到的是一篇拦截说明。
这些数字来自运行时探测，不是需要溯源的游戏事实。所以覆盖声明与缺据声明同等对待：
**由代码生成、不经模型**。改后该问题 0 token、0 拦截。

## 2026-08-18（第三轮）· 表格继承前一句的绑定

改前拦截里最大的一类是「整张表都没绑定」：模型的自然写法是
`腰带上的力量词缀档位如下[[E1]]：` 紧跟一张表。引导句绑定了证据、表格是它的续写，
但分句后表格成了独立单位、自己没有标记，于是整张表被判「事实句未绑定引用」。

**先量再改**：104 句拦截里 17 句是这种形态，其中 13 句紧邻前一句有绑定可继承，
而且**继承后 13 句全部通过数值回填校验**（0 句需要继续拦）——说明它们的数字本来就在
证据里，拦它们是错误拒答。

安全前提是：**继承只提供编号，数值校验照旧跑**。表里编造的数字继承编号也救不了它。
另外三条限制：只有表格能继承（普通句子不是引导句的续写）、只继承**已通过校验**的
那一句（被拦的句子不能当依据来源，否则一句无据断言能把绑定「传染」给整张表）、
表格自己有标记时以它自己的为准。

| 指标 | 上一轮 | 本轮 |
| --- | --- | --- |
| 引用有效率 | 62%（170/274） | **67%**（183/274） |
| 拦截总数 | 104 | **91** |
| 「表格块未绑定」 | 17 | **4**（剩下的是紧邻前一句本身也被拦） |
| 流式与批量判定一致 | 34/34 | **34/34** |
| 单测 | 370 | **378** |

检索侧不变：Recall@5 100%、错误拒答 0%、上游漏出 6%（1/16）。

### 人工审计暴露了一个成族的问题：**元说明句被拦**

放行表格后 blocked 池换了成分，补判 5 条，判出 3 条新的错误拒答。它们指向同一个缺口——
**项目自己要求模型说的那些「元说明」句反而被闸门拦掉**：

| 被拦的句子 | 为什么该放行 |
| --- | --- |
| 「共 38 个 ladder，本次返回 6 个，**结果被截断**」 | 项目规则明写「枚举类工具静默截断等同于漏答，超出上限必须写出还剩多少」。拦掉它的后果正是那条规则要防的：用户拿到残缺清单却没有截断提示 |
| 「括号内百分比…**不等于**任何通货或工艺的一次使用成功率」 | `agents/knowledge.py` 里 `affix_pool_odds` 的规则**明确要求**模型这么说。一边要求、一边拦截，是自相矛盾 |
| 「根据已检索证据，…可从以下渠道获得或受其影响。」 | 纯引导句、无数值，只是以句号而非冒号收尾 |

前两条不是「白名单再放宽一点」能解决的，它们的正解不同：

- **截断声明**：数字（38/6）来自工具的 `meta` 而非证据卡片，所以不该无条件豁免，
  而应让工具把截断信息作为**可引用内容**交出来。
- **口径免责**：提示词要求的句式是固定的，可以按固定句式识别——与
  `bench_catalog` / `metamod_matrix` 的 scope 规则同一个思路（正向匹配原字段，
  而不是扩充同义词黑名单）。

审计错误拒答率因此回到 33%（4/12）。**注意这不能与上一轮的 9% 直接比**：blocked 池是
「当前仍被拦的句子」，每修好一类，池子就换一批更难的进来。跨轮次要看的是拦截总数
（192 → 104 → 91）与已修类别数。

## 2026-08-18（第四轮）· 元说明句改由代码附注，并撤销一次提示词改动

上一轮判出的那族错误拒答——**项目自己要求模型说的话被项目自己的闸门拦了**——本轮按
「代码生成、不经闸门」的既有思路修掉，同时**用测量否决了自己的第二个改动**。

### 改动 A（保留）：`orchestrator/loop._answer_notes()`

三类边界声明改由代码从工具返回值里取值生成，附在答案末尾（批量加 `> ` 引用块，
流式发 `{"type":"note"}`）：

| 附注 | 取值来源 | 为什么不能让模型说 |
| --- | --- | --- |
| 枚举被截断，共 N 项只返回 M 项、剩余 N−M 项未列出 | 工具 `data` 的 `truncated` / `*_total` / `*_returned` | 实测 `mod_tiers` 的 `ladders_total=21 / returned=6` **只在工具 data 里，卡片一个字都没有**，模型只能无绑定地说 → 被拦 → 用户拿到残缺清单却看不到截断提示 |
| 某些渠道尚未采集 / 已采集但零命中 | `coverage_note`、`channels_no_match_note` 逐字透传 | 同上，且改写它等于改写覆盖事实 |
| 括号内百分比是同组生成权重占比，不等于成功率 | 证据里出现 `1500（1.888%）` 形态时触发 | 提示词**明确要求**模型这么说，一边要求一边拦截是自相矛盾 |

选代码附注而不是加白名单豁免：豁免等于允许模型自己编这些数字。附注走的是与缺据声明、
覆盖声明同一条路——代码生成、完全可预测。附注自己不带 `[[E]]` 标记
（否则引用列表会出现没被任何句子用到的编号，有单测钉住）。

端到端实测（「法杖上的法术伤害词缀有几档」）：答案末尾出现
「**本轮枚举被截断**：`mod_tiers` 命中 21 项，只返回了 6 项…剩余 15 项未列出」与权重口径附注。

### 改动 B（**已撤销**）：让提示词告诉模型「这三类声明不用你自己说」

想法是既然代码会附注，就让模型别再复述，省下那几句被拦的元说明。加了一段约 9 行的说明后
重录 20 条受影响用例，结果**整体明显变差**：

| 指标 | 改动 B 之前 | 加了提示词段落 |
| --- | --- | --- |
| 引用有效率 | 67% | **55%** |
| 拦截总数 | 91 | **122** |
| 元说明类拦截 | 6 | 3 |

换来 3 句、赔掉 31 句。**判因不能只看两次数字**——模型输出有轮次波动，所以撤掉段落后
把回归最重的 5 条各重录一次，同一把尺（当前 `verify()`）三向对比：

| 用例 | 旧提示词（已提交） | 新提示词 | 旧提示词（重录） |
| --- | --- | --- | --- |
| `desc_steal_mods_belt` | 5/22 | 20/30 | 6/14 |
| `name_ascendancy_conjoined_spire` | 0/7 | 6/11 | 3/12 |
| `num_max_resistance_cap` | 7/19 | 13/26 | 5/20 |
| `desc_headhunter_effect` | 4/15 | 10/20 | 4/20 |
| `num_max_phys_reduction` | 3/12 | 6/10 | 3/12 |
| **合计拦截** | **19** | **55** | **21** |

15 条录制恢复到旧提示词版本，5 条保留新录制。

**教训（比改动本身重要）**：

- **在提示词里解释闸门机制会让模型整体变糟**，不只影响被提到的那几句。原因可以猜
  （注意力被占、就在 `# 引用绑定` 之前），但机制不重要——重要的是这类改动**必须先量**。
  提示词看着「只是多说了一句」，实际是全局改动，与改代码里一个分支完全不同。
- **两次数字的差不能当因果**。判因至少要有同条件的重复运行；这里的成本是重录 5 条
  （约 12 万 token），换来一个明确结论，值得。
- 别拿录制里存的 `blocked_claims` 跨轮次比：那是**录制当时**的代码算出来的。旧录制早于
  表格继承与白名单改动，存的数字本身过期（同样 20 条，存的是 125 → 106，实际是 70 → 106，
  结论正好相反）。跨轮次比较**只能**用当前 `verify()` 重跑。

## 2026-08-18（第五轮）· 两条路径合流：修掉一个结构性漏改

按 `.claude/ENGINEERING.md` 做全局 review 时发现的，不是靠指标发现的——**指标发现不了它**，
因为评测的 `--gate` 只重放录制、走不到编排层。

`run_turn`（300 行）与 `stream_turn`（299 行）是同一条流水线的两份实现。逐行对完有三处分叉：

| 分叉 | 后果 |
| --- | --- |
| **「偏好工具零证据兜底」只写在批量路径** | 流式下答案带着零条证据进闸门、每个事实句被拦，用户看到一篇拦截说明。批量那段注释自己写着这种结果「比一句查不到更糟，而且掩盖了本轮其实无据这个事实」 |
| 「检索不可用」两套措辞 | 同一故障两种说法 |
| `degraded_note` 在覆盖声明路径上一边设一边不设 | 降级提示时有时无 |

反例仍然拦得住：`猎首会偷取词缀，说明如下：`（句首是实体名）、

**C. 缺据声明构式被三处叠加原因切断**

`所提供的 16 条证据中，**没有任何一条**直接陈述"…"。` 被拦，原因叠了三层：`陈述` 不在

夹着领域名词时构式不成立，那是游戏事实断言而不是信息缺失声明。

### 三处继续修正（都是上一轮自己留下的半成品）

**A. 展示的对手仍来自同名组。** 上一轮改成「按 ilvl 对齐」，但候选池还限在同名组里。

最佳重合的是另一个组，于是展示出来的仍然是不相干的那条。候选池改取自 `best_group`。

**B. 一致性判定仍只在同名组里做。** 修好 A 之后立刻看出来：POEDB「附加 (13-17) - (28-32)
基础物理伤害」与 PoB「Adds (13-17) to (28-32) Physical Damage」**区间与词缀名
（砥砺的/Honed）都对得上**，只是两条阶梯各自多几档、卡在重合度 <1.0。

判据从「逐档全等」放宽到 `>= LADDER_MIN_OVERLAP`（仍要求对手唯一）：1392 → 691。

**C. 身份不唯一 ≠ 数值不可判。** POEDB 弓上的火焰/冰霜附加伤害阶梯完全相同
（GGG 给三元素同一组数值），词缀名也同为「升级的/Upgraded」——连词缀名锚点都分不开。
但三个 PoB 组里那一档的区间是同一个：**无论正确对手是哪个，取值都一样**。
所以规则细化为「**在每一个候选身份下都一致**才判一致」，并单独计数
（`ladder_ambiguous_agreed` 437）——混进普通 agree 里就等于声称验证过了身份，
而实际上只验证了数值。691 → 254。

锚点。映射本身很干净：436 个中文名里 81% 唯一，且明显正确（野蛮之→of the Brute、

## 2026-08-18（第十轮）· 唯一装备对账：归一化缺口 + 一条方向写反的提示

词缀对账收口后转到唯一装备侧的 222 条 `unique_review`。同一套方法：先看差异的**形态**，

### `norm_ranges` 在两个脚本里各写了一份（逐字相同）

合并到 `parsers/mod_bridge`（阶梯原语已经在那），顺手补上一处归一：

**端点排序**。区间是一组取值，端点顺序是**呈现**而不是事实。PoB 对减益类词缀按降序存
（`(50-40)% reduced ...`），POEDB 写 (40-50)。不排序就把 `Song of the Sirens` 的
[40,50] 与 [50,40]、`Plume of Pursuit` 的 [20,30] 与 [30,20] 报成数值分歧——
我们自己的归一化缺口，不是两源打架。

**符号不动**。POEDB 把「移动速度减少 (15-10)%」记 -15..-10，PoB 存 15..10 靠文本里的
`reduced` 表方向。抹掉符号能让更多行「对上」，但会连「一侧把加号看成减号」这类真错误
一起吞掉。所以单独识别（`same_magnitude`）、**单独计一栏**（6 条），既不算一致也不算分歧。
实测样例：Bramblejack [-15,-10] vs [15,10]、Ashrend [-60,-30] vs [30,60]。

`ranges` 差异 119 → **109**，实质字段全一致 1019 → **1024**（84.3%）。

### 脚本自己的一条提示，方向是反的

报告里长期印着：

> 【采集缺口】level_req 跳过 926/1215（76%）：POEDB 侧多数唯一装备没抓到需求等级，
> PoB 侧有值可回填。装备分析需要这个字段。

实测把方向查清楚：已配对 1215 件里 **PoB 缺、POEDB 有 = 926（76.2%）**，两侧都有 289，
**POEDB 缺 = 0**。也就是说需求等级**不是采集缺口**——POEDB 侧一直是全的，装备分析要的字段
本来就在库里；缺的是 PoB，而 P2 缺字段不影响下游（答案以 P1 为准）。

这条提示大概率误导过判断（它写着「装备分析需要这个字段」，读起来像是缺数据）。
改成按字段打印**跳过的方向**，并写明只有「POEDB 缺」才算本项目的采集缺口：

```
    base_type          POEDB 缺 1，PoB 缺 5

    ranges             两侧都缺 92
```

**只记跳过总数不记方向，就等于把「对方没数据」和「我们没采」混成一件事。**

## 2026-08-19（第十二轮）· 技能石入库：拒答变回答，同时把边界钉死在「伤害不给」

上一轮让系统学会拒答技能石问题，靠的是「这个领域一条都没入库」。这一轮把它真正入库：
**810 颗宝石（548 主动 + 262 辅助）+ 30422 行每级字面值**，`skill_gem` / `support_gem`

### 为什么它是最该做的那一个

八个 `harvested` 领域里，技能石的三张 POEDB 页面（2.2MB）**早就在 `data/http_cache` 里**，
PoB 侧结构也完整。桥接键是 `grantedEffectId`：它同时出现在 POEDB 清单页的
`data-hover="?s=Data\GemEffects/<id>"` 上，不分大小写配对**810/861 = 94.1%，零多解**。
未桥接 62 条按成因登记（`pob_missing` 51 = POEDB 保留的历史/未上线条目，
`no_zh_name` 11 = 清单页没有对应条目）。

而 `tasks.md` 里写着「技能石有阻塞，需先补 POEDB 中文页」——**那句是错的**，
中文名与中文标签都在那张缓存页上。这是同一种错误的第五次（见规约 6b 的清单）。

### 三条实测结论推翻了原本的写法

| 原本打算 | 实测 | 结果 |
| --- | --- | --- |
| 卡片写属性需求（力/敏/智） | `Gems.lua` 的 `reqStr` 是**换算系数**：真需求 = `round((20+(等级需求-3)×3)×(系数/100)^0.9×statType)` | 整个维度不入库，划进未采集 |
| 蜕变宝石按 slug 里的 `_of_` 判 | 误判 23 条：火焰净化（Purity_of_Fire）、箭雨（Rain_of_Arrows）、灰烬之捷（Herald_of_Ash）本来就带 of | 只认 `AltX` 后缀（213 颗） |
| 同键多名整条丢弃 | 7 颗是**同一颗宝石的两种官方译名**（魔卫复苏/僵尸复苏、召唤魔侍/召唤骷髅） | 正名 + 另译进别名表，两种问法都命中 |

数值口径全部取自 PoB 自己的 `GemTooltip.lua`，不是猜的：消耗要除 `Costs.lua` 的 `Divisor`
（六个 `*PerMinute` 是 60）、`manaMultiplier` 显示值是 **+100**（CWDT 存 150 → 250%）、
`damageEffectiveness` 是 **×100**。三个口径写错任何一个都会输出带引用的错数字。

### 伤害不入库，是决定不是遗漏

PoB 每级的伤害是**乘数**（冰霜新星 1 级存 `0.8 / 1.2`），要配 `baseEffectiveness` 与
`statInterpolation` 按公式算才是显示值——那属于 `calc/`（未实现）。所以：

- 表里**没有伤害列，也不留空列**（留了下一个人会以为待填，然后把乘数当伤害写进去）；
- **卡片里连「伤害」两个字都不出现**。这不是文风：充分依据的判据是查询实义词在
  `chunk.text` 里的覆盖率，把「伤害」写进 810 张卡等于给每个含「伤害」的问题送覆盖率，
  而上一轮刚把漏出压到 0%。`damage_effectiveness`（附加伤害的效果）也只在工具里给、
  标签写全名——它是加成系数不是技能伤害，进检索证据就会被当成伤害答出去，

### 闸门：领域识别多了一条通道

  「全局物理伤害提高 60%命中值提高 100%」——数字与下一条属性的名字连在一起，
  既没法读，也会让出口的数值回填对不上原文。
- **`entity_id` 必须带内容摘要**。同 (来源, 名字) 有多档（「死眼」的伤害 30% 与 20%），
  只用前两段做 id 会让后写入的 UPSERT 覆盖前一条——实测 183 行只落 171 个实体、
  悄悄丢了 12 张卡。

### 幽魂：有数据但**故意不建卡片**

1948 行是「名字 + 两个倍率」，卡片之间高度雷同，而怪物名里有大量通用词（「恶魔」27 条、
「守卫」「弓箭手」）。给它们建卡片 + 别名，等于让任何含这些词的问题都被注入一堆
近似重复的候选——词缀梯度卡踩过这个坑，那两个补偿层最后都被删了。

所以幽魂走**表 + `spectre_stats` 工具 + 「幽魂」意图词路由**。可达性必须靠路由挂上：
不挂就是一个死了的能力（元词缀矩阵在库里躺了很久没人调用过，教训在那）。

身份键也有个坑：`data-hover` 有两种形态，tooltip 缓存哈希**不是种类 id**——
2026-08-13 的缓存里 407 行走这条路、其中 7 例撞哈希，每例都是同名同 slug 但两套倍率的
不同种类（「无名猛兽」276/360 与 374/585）。只用哈希会把它们合并成一条，所以把倍率
并进键。（8-19 重抓后这条路只剩 27 行、0 例撞哈希，但**留着**：占比是页面渲染方式
决定的，会回来。）

### 不做倍率排名，是数据边界不是漏做

「生命倍率最高的幽魂是哪个」答不了：清单里混着开发用怪物（「测试之灵」10000%/10000%），
把它排第一虽然有出处，但对玩家是错答案。要排名得先能区分「实际可用」——PoB
`Data/Spectres.lua` 有 268 条确认清单（还带四抗性与技能列表），实测按 slug→英文名
能与本表命中 297 行。**接它是下一轮的事，接上之前不给排名。**
黄金集里 `gap_spectre_ranking` 钉住这条。

### 闸门：泛化意图词不能取消专指领域的缺口

新增判据 `_drop_subsumed_coverage`。实测反例：「惊悸迷雾怪物词缀的生成权重是多少」——
`monster_mod` 靠「怪物词缀」命中且权重正落在它的未采集维度，而 `mod_affix`（装备词缀，
已全量入库）靠泛化的「词缀」「权重」命中被记为 covered，于是
「有一个领域覆盖到就不拦」把缺口取消了，模型拿到的是**装备**词缀的权重。

判据只取「子串」这一档（「词缀」⊂「怪物词缀」）：不做同义词或语义相似度，
那会把复合问题也误判成同一主语，而复合问题必须保留部分作答的能力。
成对用例：这条拦住 + 「猎首有哪些词缀，值多少钱」照旧放行。

### 两处测量本身的问题（这是第四、第五次）

- **评测没模拟「路由豁免」**。幽魂问题在线上豁免检索不足（证据不在 chunk 里），
  而 `eval_run` 只算 `sufficient`，于是线上答得出来的问题在指标里显示为错误拒答。
  已按线上同序补上（精确路由优先、其次偏好工具），并且 `passed` 与 `is_wrong_refusal`
  用同一套规则——先前只改了后者，同一条用例会「不算错误拒答但仍显示 FAIL」。
  豁免会在明细里印出来，不让它变成看不见的免检通道。
- **三条不作答路径共用了一套契约**。缺据声明要说「查不到」，但越界声明**不能**
  说这句（项目自己的规定：那会让用户以为游戏里没这东西），而精确路由的不作答理由
  由工具给出（「来源该格为空」「没形成确定调用」）比「查不到」更准确。
  三条路径的契约已分开，`Recording` 加了 `out_of_scope` / `precision_route` 两个
  结构化标记（不靠嗅答案文本）。**先前 5 条用例长期挂在这个错契约上**：
  3 条 POE2 越界从来没被录制过，另 2 条每轮都报 FAIL 而没人当回事。

## 2026-08-19（第十四轮）· 幽魂接上 PoB：抗性、排名，以及需求 15.5 第一次真正可验收

上一轮把「不支持倍率排名」写进覆盖声明，就是在等一份能区分「实际可用」的数据。
PoB `Data/Spectres.lua` 就是它：**268** 条建模数据，带四抗性、护甲/闪避/能量护盾系数、
攻击间隔与怪物技能 id。

### 两侧是同一个量的不同单位，所以可以对账

实测（按 slug→英文名 配对的 200 个单行名字）：POEDB 的百分数 ÷ 100 与 PoB 的小数
**逐条相等**的占 91%（生命）/ 94.8%（伤害）。差异分两类，**分开落库**：

| 类别 | 条数 | 含义 |
| --- | --- | --- |
| `kind='spectre'` | **8** | 两侧各只有一条却对不上 → **真分歧**，并列展示 |
| `kind='spectre_review'` | 43 | POEDB 有多个同名种类、PoB 只建模一个 → 粒度差异，**不当冲突呈现** |

把粒度差异记成分歧，就是把「谁记错了」和「谁记得更细」当成一件事——词缀对账那轮
2729 条「待核对」里绝大多数其实是配对判据错，教训在那。

### `citation.conflict_block` 从不可达代码变成生效路径

需求 15.5 要求确认冲突并列展示。这个函数**从写下起就没有调用方**——因为
`kind='mod'` 的已确认冲突长期是 0 条，没有东西可展示。8 条幽魂真分歧给了它第一份数据：

`spectre_stats` 把渲染好的块放进 `data["conflict_block"]`，由 `loop._NOTE_FIELDS`
逐字附在答案末尾。**不让模型转述**：那几个数字来自两个来源，模型说出来只能无绑定地说，
然后被自己的闸门拦掉——这是同一个模式的第六次，所以直接走既有机制。
黄金集加 `cross_spectre_conflict`（水手咒灵：POEDB 生命 100%/伤害 165% vs PoB 1.0×/1.32×），
录制实测答案里两个来源都在。

### 排名的依据是「PoB 建模过」，不是「数字大」

POEDB 的 1948 条里混着开发用怪物（「测试之灵」10000%/10000%）。PoB 只建模玩家实际会用的，
所以它同时是一份确认清单——排名在这 268 个里做，并在答案里写明范围。
`gap_spectre_ranking` 因此**从拒答用例翻成可答用例**（`rank_spectre_life`），
这是上一轮那条边界被解掉的凭证：解法不是放宽判据，而是补上能区分「实际可用」的数据。

同时把 `抗性` / `最高` / `排名` 这些词从 `spectre` 的 `missing_dimension_hints` 里**删掉**。
留着就是镜像版本的老毛病：能答的问题被自己的覆盖声明拦成缺口。剩下两维（掉落、
怪物技能的中文说明）确实还没有——`gap_spectre_drops` / `gap_spectre_skills` 钉住。

### 怪物技能有数据但不可呈现

`skillList` 里是 `MonsterLightningThorns` 这类内部 id。实测 **1235 个 id 与本库 810 颗
宝石的 `grantedEffectId` 零命中**——它们不是玩家宝石，没有中文名可给。存进
`pob_spectre.skill_ids`（将来接怪物技能表时它就是桥接键），但不进卡片、不进工具正文。
**有数据不等于可呈现**，这与怪物词缀里那 63 条「只有内部 stat id」是同一条判据。

### 又是两处测量本身的问题（第六、第七次）

- **`partial_note` 里写了具体数字**（「测试之灵 10000%」）。它会注入系统提示词，
  模型照着复述就是无绑定断言——录制里真的拦到了这一句。数字挪回 BASELINE 与代码注释，
  声明只留「混着开发用怪物」。**提示词里的数字都有这个问题**，不只是这一处。
- **录制没有存「用户实际看到的答案」**。`raw_answer` 是模型的待检材料、`binding.text`
  是回放闸门的结果，两者都**不含代码附注**——于是「附注是否真的到达用户」以前没有
  任何东西在验证。实测撞到：`cross_spectre_conflict` 要求答案里并列两个来源，而冲突块
  正是代码附上的，按 `binding.text` 判就永远缺失。`Recording` 加 `final_answer`，
  答案内容类契约一律按它判。

顺带把 PoB 的生命/伤害系数也放进工具证据表：冲突并列里出现的数字**必须在证据里**，
否则模型只能无绑定地说。这一改让这几条用例的引用有效率从 38% 回到 62%。

## 2026-08-19（第十五轮）· 天赋树连接关系入库：「点到某节点要几点」从拒答变可答

`passive_tree` 的 `partial_note` 从第一轮起就写着「**天赋点消耗与连接关系未入库**，
因此无法回答「点到某节点要花几点」」。这一轮把它做了——而数据**一直在手上**：
树 JSON 就在 `data/http_cache` 里、每次采集都在解析，只是 `in`/`out` 与 `classes`
没被取出来。与元词缀矩阵、技能石同一个形态：缺的是抽取那一步，不是数据。

入库：`passive_graph_node` **3390** 个节点（可经过 2478）、`passive_graph_edge`
**3382** 条无向连线、`passive_tree_meta`（总点数 123、升华点 8）。
节点 id 就是 GGG 的 skill id（实测 3389/3389 与 JSON 键相等），能与天赋卡对上。

### 三个数字先后错了三次，都是判据问题

| 判据 | 「野蛮人 → 女巫」 | 最远距离 |
| --- | --- | --- |
| 直接把 `in`/`out` 当无向边 | **2 点** | 19 |
| 排除 root（树心） | 22 点 | 33 |

第一版为什么错：**7 个职业起点都连在 `root` 上**，而游戏里不能从一个职业穿到另一个职业。
2 点这个数字荒谬到能一眼看出，所以它被抓住了——但如果错得不那么离谱（比如只差两三点），
它会直接变成一个带引用的错答案。所以这一轮的验证方式是**先找一个自己知道答案的量**
（两个职业起点之间的距离必须很大），而不是看结果「像不像」。

另两条排除同样是游戏规则，写进表注释：升华节点只能从升华起点进入、大师天赋不作为通路。
珠宝插槽**可以**经过——游戏里它就是个能点的节点。

### 答案必须按职业给，还必须带路径

同一个基石「神威之盾」：圣堂武僧与野蛮人 11 点、贵族 15、女巫 16、决斗者 17、
暗影 24、游侠 25。**给一个笼统的数字就是错答案**，所以工具按七个职业分别给。

点数是 BFS 算出来的，不是原文，所以整条路径逐节点列进证据——用户能照着核对到边一级。
这是「算」与「猜」的分界线。

### 两个实现细节，都是实测逼出来的

- **起点标签要用职业名**。JSON 里贵族与暗影的起点节点自己叫「七」「六」（占位名），
  照搬出去用户看不懂。职业名取自顶层 `classes` 数组。
- **每个职业一次 BFS，不是每个同名位置一次**。「力量」在树上有 73 处，
  逐位置跑是 7 × 73 = 511 次 BFS，实测单次查询 **327ms**；改成一次 BFS 找最近目标后
  **3–6ms**，结果不变。BFS 本身按距离扩展，第一个命中的目标必然最近。

### 边界跟着数据前移（这是第三轮做同样的事了）

`missing_dimension_hints` 里的「要花 / 几点 / 怎么走 / 路径」全部**删掉**——
留着就是让闸门把能答的问题声明成缺口。`gap_passive_path_cost` 从拒答用例翻成
`num_passive_path_cost`（期望值 11）。仍缺的两维补上哨兵：
`gap_passive_cluster_jewel`（星团珠宝上的天赋不在主树上）与「值不值得点」（取舍不是事实问题）。

**同一个测试的期望也跟着改了**：`test_partial_domain_gaps_when_asked_dimension_is_the_missing_one`
原先拿「点到某节点要几点」当「问缺的那一维」的例子，现在换成星团珠宝。
用例要跟着数据走——留着一句已经不成立的边界，比没有用例更糟。

## 参数标定结论（2026-08-17）

- **`retrieval.min_coverage` 保持 0.5**。扫描 0.30–0.80：0.30/0.40/0.50/0.60 四档结果
  完全相同，0.70 起多一条错误拒答，0.80 才多拦住一条漏出且再多一条错误拒答。
  漏出走的是「实体精确命中」分支，根本不经这个阈值——**调它压不住漏出**。
- **`retrieval.factual_terms` 当前不改变任何结果**。全部生效与完全清空，拦截数都是 120。
  因为 `classify` 的默认就是事实句，词表只是提前命中一步。触发路径分布：
  有绑定标记 158 / 命中本词表 66 / 命中库内领域词 30 / 含数值 4 / 兜底默认 12。
  保留它是为了将来——若把默认改成「过渡句」，它会立刻变成主判据。

### 两个测量本身的 bug（已修，记下来避免重犯）

- **工具名取错键**：`_tool_record` 存的是 `tool` 而我读了 `name`，于是每条工具调用都录成
  空串、路由指标恒为 0/6。指标为 0 时先怀疑量错了，再怀疑功能坏了。
- **新鲜度误报**：初版拿一次裸检索的整体指纹去比录制，但一轮问答的证据集还包含模型
  中途调工具追加的部分，于是所有调过工具的录制都被误报为「过期」（实测 3 条）。
  改为按 `chunk_id` 逐条比正文，且判据是**包含**而非相等——证据 text 是按 1200 字截断的
  快照，要相等会把每条被截断的证据都报成过期。
