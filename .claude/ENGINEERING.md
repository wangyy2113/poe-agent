# 研发规约

迭代 poe-agent 的硬性工作方式。这里的每一条都来自本仓库真实踩过的坑，不是通用箴言——
读到某条觉得「这不是显然的吗」，请看它后面括号里的实例：那都是已经犯过的错。

根 `CLAUDE.md` 里有本文件的摘要（只有 `CLAUDE.md` 会自动进上下文，这个文件不会），
两者冲突时以本文件为准。

## 1. 先全局 review，再动手

任何非平凡改动之前，先把这四样看完，不要凭上下文里的印象：

| 看什么 | 为什么 |
| --- | --- |
| 目标模块的**模块 docstring** | `binding.py` / `hybrid.py` / `loop.py` 顶部记着「为什么不这么写」，包括已被删掉的两个补偿层 |
| `tests/golden/BASELINE.md` | 闸门与检索的历史结论，含两次「测量本身写错」和一次被否掉的改动 |
| 同一规则的**其它实现处**（见第 5 条清单） | 漏改成对点是本仓最高频的缺陷 |
| `.kiro/specs/poe1-agent/` 相关需求条目 | 规格是真源；`tasks.md` 的复选框在阶段 1b 之前不可信 |

「全局」的含义是**先判断这个改动该落在哪一层**，再写代码。层选错了，写得再干净也是补丁。

## 2. 顶层视野：先定层，再写码

本项目的层次是有优先序的，越靠上越可预测：

```
代码生成（缺据声明 / 覆盖声明 / 越界声明 / 答案附注）   ← 完全可预测，优先
  ↓
代码闸门（充分性判定 / 维度闸门 / 出口绑定校验）        ← 可预测，模型不听话时兜住
  ↓
结构化工具（精确算得出来的一律走工具）                  ← 精确但依赖数据覆盖
  ↓
提示词（只是第一道约束，不是唯一约束）                  ← 最不可预测，全局副作用
```

判据：**能在上层解决的问题，绝不放到下层。**

- 边界声明（截断计数、覆盖声明、权重口径）→ 代码生成层。它们的数字不在任何证据里，
  让模型说就只能无绑定地说、然后被自己的闸门拦掉（第四轮：`_answer_notes()`）。
- POE1/POE2 边界 → 代码层，且判据在**原始问题串**上匹配。放到覆盖率或分词之后就漏
  （实测「poe2 词缀怎么洗」分词后拿到 100% 覆盖率、被判依据充分）。
- 「某属性能从哪来」→ 工具层枚举，不是 `kb_search` 语义召回。不完整的枚举被当成完整的呈现
  就是错误答案。
- **改提示词是全局改动**，会拖垮它没提到的那些句子。第四轮实测：加 9 行说明让引用有效率
  67%→55%、拦截 91→122，已撤销。

## 3. 大胆重构，拒绝补丁式改动

出现下面任一症状，就**不要再加一个分支**，停下来重构：

- 同一个概念在多处各写一份判据（例：句子类型判定若在批量与流式各写一套，就必然分叉；
  现在 `StreamingGate` 强制复用批量 `verify()` 的分句与判定函数）。
- 正则白名单不断加项，且新项与旧项在语义上重叠。**正解通常是正向匹配原字段，
  而不是扩充同义词黑名单**（`bench_catalog` / `metamod_matrix` 的 scope 规则就是这么定的）。
- 出现按用例名 / 问题串特判的 `if`。评测用例是**度量**，不是分支条件；为了让某条用例过
  而加的特判，等于把度量废掉。
- 排序层反复加权、限流、调系数 → **先怀疑索引切分粒度，再改排序**
  （`retrieval/hybrid.py` 顶部记着两个因此被删掉的补偿层）。
- 函数长到读不完、或一个函数里同时做「取数 / 判定 / 生成文本」三件事。
  `orchestrator/loop.py` 是本仓最容易长胖的地方，它已经是第二大文件。

重构的安全网是现成的，用它而不是靠小心：单测 389 项秒级跑完、`eval_run.py --gate`
离线重放、流式与批量一致性 34/34。**重构前后这三样数字必须持平或变好**，
其中评测两项要成对看（错误拒答 ↔ 无据漏出，只压一头不算完成）。

## 4. 该删就删

- 删掉的东西要有替代者或被证明无用，**不留「以后可能有用」的函数**。
- 不为兼容自己刚写的旧行为留分支。改判据就改判据，不要 `if new_mode:`。
- 发现某个约束本身是**假的**，删约束而不是绕开它（实例：`pob_base_item` 上的
  `UNIQUE(name_zh)`——POEDB 把两个不同底材译成同一个中文名，这个约束一开始就是错的，
  删掉才对，加后缀去重就是把错误固化）。
- 删除必须证明没丢能力：跑单测 + `--gate` + `check_doc_facts.py`，并在 PR 里说明删了什么、
  凭什么判定它无用。
- 死代码留着的代价是具体的：下一个人会以为它在生效，然后照它的语义改别处。

## 5. 防漏改：本仓已知的成对点

改动落在左列任一处，右列**必须同时确认**。这是漏改缺陷最集中的地方：

| 改这里 | 必须同时确认 |
| --- | --- |
| `binding.verify()` 的分句或判定 | `binding.StreamingGate`（一致性测试 10 组文本 × 4 种切片粒度） |
| 出口闸门规则 | `agents/knowledge.py` 提示词——**一边要求模型说、一边拦掉它**已经发生过 4 次 |
| 工具的返回字段 | `tools/registry.py` 的 schema、`orchestrator/loop.py` 的 `_CODE_INVOKED_TOOLS` 与附注字段 |
| `kb/coverage.py` 的领域意图词 | 意图词必须**专指**：曾把「怪物」当 boss 意图、「知识库」当路由意图、差点把「降临」当 POE2 标记（POE1 有「先祖降临」） |
| 采集器抽取字段 | `kb/render*.py` 卡片切片、`retrieval` 的别名与词表 |
| `core/db.py` 的 SCHEMA | 迁移函数**幂等**，且判据用真实 schema 而不是 SQL 文本匹配（曾因注释里出现 `UNIQUE(name_zh)` 字样导致迁移每次启动都跑） |
| 任何写进文档的数字 | `scripts/check_doc_facts.py` 里注册断言，别让文档重新落后于代码 |

## 6. 防埋坑：先量后改，量对了再改

- **改闸门、检索阈值、提示词之前先跑评测拿基线，改完再跑一次。** 这是本项目唯一能判断
  「收紧规则」是变好还是变坏的手段。
- **两次数字的差不能当因果。** 模型输出有轮次波动，判因至少要有同条件的重复运行
  （第四轮：旧提示词两次独立运行 19 / 21 句，新提示词 55 句，才敢说是提示词造成的）。
- **别拿录制里存的 `blocked_claims` 跨轮次比**——那是录制当时的代码算出来的。跨轮次比较
  只能用当前 `verify()` 重跑（同一批用例，存的数字 125→106 看着变好，重跑是 70→106 实际变差）。
- 先确认**测量本身是对的**。BASELINE 里记了两次测量写错：工具名读了 `name` 而不是 `tool`
  导致路由指标恒为 0；新鲜度比对用了裸检索的指纹导致所有带工具的录制都被误判过期。
- 改完把结论与数字写进 `BASELINE.md`，**包括被否掉的改动**——否决理由比成功改动更值钱。

### 6b. 注释与文档里的**因果结论**必须抽验，它们比数字更容易长期骗人

`check_doc_facts.py` 能拦住数字漂移，拦不住**判断**。连续四轮里最有价值的产出都不是新功能，
而是发现项目自己写下的判断是错的：

| 项目自己写的 | 实际 |
| --- | --- |
| 「`craft_metamod_interaction` 需联网跑」 | 采集只抓 POEDB 镜像，而那页一直在 `http_cache` 里、抽取器跑得通（134 条） |
| 「跨来源冲突缺的是人工核对，不是代码」 | 配对判据错了：按组名配对，而组名两侧系统性不同（同名组仅 11.5%） |
| 「表头那格不是数字，fullmatch 已排除整列，所以 values 全部来自数据行」 | 前半句对、后半句由此**不成立**，`_index_column_numbers` 从未生效 |
| 「`level_req` 跳过 926：POEDB 侧没抓到，PoB 侧有值可回填」 | 方向正相反：POEDB 全有、PoB 缺 926 |
| 「`_BINDING_RE` 支持 `[[E1][E3]]`」 | 认不出来，有据的句子被判未绑定 |

共同点：**每一句都自洽、都看着可信**，所以能在注释和文档里存活很久，并让后来的人照着错的
前提做决定。抽验动作：

- 读到「需要联网 / 需要人工 / 不可能 / 已排除 / 已支持」这类**判断**时，去看它依赖的那个
  事实还成不成立：抓哪个 URL、缓存里有没有、函数真跑没跑、方向是哪一侧。
- 一句注释若声称「因为 A 所以 B」，**分别验 A 与 B**。上表第三行就是 A 真 B 假。
- 注释写实测数字时带上口径（哪一批、什么时候、多少分之多少），否则下一个人无法复核。
- 发现写错了，**改掉并写下正确结论**，不要只在别处补一句新的——两句并存时读者会信先看到的。

## 7. 收口：改完就提 PR

顺序固定，缺一步都不算完成：

```bash
.venv/bin/python -m unittest discover -s tests -t .    # 全绿
.venv/bin/python scripts/eval_run.py --gate            # 与 BASELINE 上一轮对比
.venv/bin/python scripts/check_doc_facts.py            # 文档数字一致
```

- 影响生成结果的改动（提示词、工具返回、证据组装）需要**重录**受影响用例，否则量的是旧路径。
  只重录真正涉及的用例，不要全量重录。
- 新一轮结论写进 `tests/golden/BASELINE.md`。
- 提交信息一句话说清**这次闭环了什么能力**；PR 正文写清指标前后对比、
  以及**这轮否掉了什么**（否决同样是产出）。
- 本机没有 `gh`：推分支后给出 `compare/main...<branch>` 链接由人开 PR。
- `semantic-review/` 是本地审查产物，不入版本库。
